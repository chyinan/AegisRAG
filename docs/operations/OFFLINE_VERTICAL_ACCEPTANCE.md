# Offline document-to-citation acceptance

## Purpose

`tests/integration/journey/test_document_to_citation.py` covers one composition
gap: a single document accepted by the actual upload API must become the same
persisted evidence returned by retrieval, query/chat SSE, persisted chat history,
and source resolution. The two parameterized variants preserve the direct query
path and exercise `/chat/stream`, the endpoint used by the workbench API client
(`apps/web/src/lib/api/client.ts`). This is API composition evidence, not a browser
interaction test.
This is new acceptance coverage, not evidence of an old-code production failure
or a production fix. No production code is changed.

## What the test connects

1. A multipart `POST /upload` uses `DocumentUploadService`, `DocumentRepository`,
   and `SqlAlchemyAuditPort`. Initial IDs are generated by the service. A fresh
   SQLite session confirms there are no chunks or embedding jobs yet.
2. Existing upload storage and queue fakes capture the actual bytes, checksum,
   byte size, and ingestion payload. Persisted upload metadata must match that
   capture, and the parse read must use its committed object key and scope.
   Those bytes feed the existing read-storage
   fake; the captured payload supplies the parse context and document/version/job
   IDs. `IngestionParseService` performs real TXT parsing, chunking, persistence,
   and embedding handoff. No chunks are manually inserted.
3. The captured embedding payload drives `EmbeddingJobService`, the production
   `FakeEmbeddingProvider`, and one shared production `FakeVectorStore`. No
   vectors or readiness flags are manually inserted. Fresh status API requests
   observe `uploaded`, `chunked`, and then `retrieval_ready` with one vector.
4. `POST /retrieve` uses the real retrieval factory: dense lookup in that same
   vector store, the SQLite sparse fallback, RRF, and the fake reranker. Both
   branches must contribute positive fusion weights to the actual persisted
   chunk. A fresh session also reads the real persisted retrieval log and checks
   both branch input counts.
5. Both `POST /query/stream` and `POST /chat/stream` use the real
   `RagQueryApplicationService`, repository hydration,
   `ContextPacker`, `PromptBuilder`, `RagGenerationService`, and
   `CitationExtractor`. A recording subclass delegates to `FakeLLMProvider.stream`
   unchanged. Its explicitly synthetic configured answer carries the canonical
   marker derived from the real persisted chunk. The actual provider request
   must contain that chunk's original text and marker. The actual SSE body must
   contain tokens, a citation, no error, and exactly one schema-valid successful
   final with the same evidence identity. Each wire event name must agree with
   its JSON payload event name.
6. The chat variant composes the same RAG service with `ChatApplicationService`,
   `ChatMemoryService`, and SQL `ChatMemoryRepository`. No session ID is supplied
   for its first turn: chat creates the session itself. The canonical successful
   final must include that generated session ID. A fresh SQL session checks the
   committed active session and user/assistant rows, actual question and answer,
   sequence, ordinary principal, status, and stored citation identifiers.
   A separate `GET /chat/history` request constructs another real service/session
   and checks those contents, `no_answer=false`, no error, and the canonical
   document/version/chunk/citation IDs round-trip.
7. `POST /sources/resolve` uses `SourceResolveService` and `DocumentRepository`
   to resolve the exact document/version/chunk tuple and original excerpt. The
   query variant uses its final citation; the chat variant uses a citation read
   back from persisted history. Both use the same normal principal as upload and
   retrieval. No memory records or citation records are seeded, and no optional
   citation-metadata persistence is added.
8. One second chat turn supplies the service-created session ID and a distinct
   synthetic question. Its sole extra purpose is actual memory prompt continuity:
   the provider's second recorded request must include the first turn's summaries
   read from the real repository, roles, sequences, and session in the dedicated
   `conversation_history` prompt. That history must contain two prior messages,
   exclude the current question and source text, and coexist with the actual
   uploaded evidence in the full generation request. No memory context is injected.
   The second stream is checked with the same full canonical SSE assertions.

Each API dependency override constructs a real service with a fresh SQL session;
no service methods or returned results are replaced. The ordinary existing
`tenant-1` / `user-1` / `knowledge_admin` test principal uses the repository's
test-only development headers and normal upload/manage/read/retrieval permissions.
Authentication dependencies and policy implementations remain unchanged.

Streaming RAG and chat audit use the real `SessionFactoryAuditPort` wrapped by
`BoundedBestEffortAuditPort`, matching the application factory's independent
auxiliary-audit boundary. Memory writes use the chat request session and its real
commits; an audit write cannot accidentally commit those rows. Mandatory query
audit remains a separate constructor dependency. The query/chat parameterization
shares the upload/parse/embedding/retrieval setup and all original assertions;
there is no duplicated setup or expanded framework/security/recovery matrix.

## Sensitivity control

An independent sensitivity run selects the original `[query]` variant and can
replace only the retrieval factory's supplied
vector store with a separate empty `FakeVectorStore`, without editing this test
or any production code. SQLite sparse retrieval can still return the same chunk.
The **unchanged positive-path contribution assertion** must fail specifically
because the dense branch did not contribute. Record that expected failing run
separately from the normal passing run. This demonstrates that sparse-only
success cannot conceal disconnected upload-to-vector wiring. It is a test-harness
negative control, not a simulated production bug fix. The normal acceptance test
contains only the two connected happy-path variants.

A separate independent persistence control can select `[workbench-chat]` and
replace only the second chat-owned repository commit with that repository's
rollback. The first user/session commit and all actual assistant writes, audit
implementations, SSE checks, and fresh-history assertions remain unchanged.
Rollback deliberately discards the assistant write and releases its synthetic
SQLite write transaction so independently owned audit can finish. Record the
active transaction before rollback and its absence afterward. The original
successful-SSE assertions must still pass, but a fresh SQL session must observe
only the committed user row and the **unchanged** `message_count == 2` assertion
must fail. Check the original source hash before and after the experiment.

This is sensitivity to a missing durable assistant write, not a simulation of a
real commit exception, recovery behavior, or a production defect/fix. A no-op
commit instead leaves the already-flushed SQLite transaction open and can
interfere with independent audit; an interrupted or incomplete control run is
inconclusive and must be retained separately. An `F` marker alone is not proof.
Use a bounded external harness, and require complete failure details, the exact
original assertion site, and all control checks before reporting success. These
post-response reads do not prove intermediate visibility or live stream timing.

## Run

From the repository root, using the existing development environment:

```sh
unset AEGISRAG_PILOT_MIGRATION_URL AEGISRAG_PILOT_RUNTIME_URL
unset AEGISRAG_PILOT_DISPOSABLE_DATABASE AEGISRAG_RLS_ADMIN_DSN
unset AEGISRAG_RLS_RUNTIME_DSN AEGISRAG_RLS_RUNTIME_USER
unset AEGISRAG_REQUIRE_POSTGRES_DURABLE
export OTEL_SDK_DISABLED=true RAGAS_DO_NOT_TRACK=true AEGISRAG_REAL_ENDPOINT_ALLOWED=0
python -m pytest tests/integration/journey/test_document_to_citation.py -q --no-cov
ruff check tests/integration/journey/test_document_to_citation.py
```

The test requires the ordinary test dependencies, including SQLite/aiosqlite and
Alembic. It migrates a disposable temporary database to the current migration
head and does not need an external service, network model endpoint, or browser.
Set `OTEL_SDK_DISABLED=true` before process startup to suppress the application's
default localhost telemetry exporter; setting it after app import is too late.
The adjacent `tests/integration/journey/conftest.py` also defaults this flag before
the journey imports the app, matching the existing framework-test pattern. The
explicit process flag remains important when other tests import the app first.
Record command output for the tested source revision; the presence of this
document alone is not a passed-run claim.

## Evidence limits

- Fake generation proves request/evidence/citation plumbing, not answer quality,
  factual reasoning, or behavior of a live model
- SQLite's Python sparse fallback does not validate PostgreSQL ranking, pgvector,
  production RLS, or a deployed database configuration
- Captured in-memory queues and object storage do not validate Redis/RQ execution,
  MinIO durability, queue transport, retries, recovery, or multi-process workers
- The shared in-memory vector store validates same-process composition; it does
  not prove cross-process vector durability
- ASGI SSE checks event content and terminal semantics, not live-network cadence,
  proxy buffering, browser rendering, or user-interface interaction
- Development headers do not validate production login/JWT/OIDC/session
  authentication
- This single ordinary happy path is not a framework matrix, security review,
  deletion/recovery test, deployment acceptance, or production-readiness verdict

README is unchanged because this adds an explicitly bounded test and its
operations note without changing product behavior, supported integrations,
configuration, or deployment claims.
